O que foi testado

Após cada publicação, o runner aplicou o pacote publicado em um diretório novo, comparou os arquivos com o checkout do GitHub e iniciou o container com devcontainer up. As configurações dos agentes eram descartáveis, sem credenciais pessoais.

  • Compose com image:, usuário vscode e workspace /workspace.
  • Python 3.12.16, Node.js 24.22.2, GitHub CLI 2.103.3, Claude Code 2.1.314, Codex 0.166.0 e Hermes 0.22.5.
  • PowerShell e importação de Terminal-Icons; configuração local do Codex e link de instruções globais.
  • Ausência dos comandos skills e sync-project-skills.
  • Persistência do cache, estado do Hermes e volume de dependências após remover e recriar o container.
  • ESP32: esptool 5.6.0 e mpremote 1.29.0, sem exigir uma placa conectada.

Comandos executados pelo workflow, após autenticar no GHCR e instalar o CLI:

bash scripts/validate-published-devbox.sh ai-devbox 0.22.0
bash scripts/validate-published-devbox.sh ai-esp32-devbox 0.1.0

Script completo de validação. O teste de comunicação USB com uma placa física permanece manual; veja o guia ESP32.

A troca da base revelou caminhos absolutos herdados após renomear o usuário vscode para hermes. Configurações, sessões e credenciais do volume foram preservadas pelo teste.

Os checks Hermes agora bloqueiam a publicação quando falham. Validação final: 37 aprovações, zero falhas, cinco verificações não executadas. Estas cinco dependem de gateway/dashboard configurados ou de abertura manual pelo Dev Containers; a conexão real com Hermes Desktop também permanece manual.
