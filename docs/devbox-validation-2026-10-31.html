Abertura do CLI confirmada pelo usuário

No container do usuário, ~/.hermes/installs pertencia a root (0:0) com permissões 755, enquanto o Hermes rodava como vscode (1000:1000). A subpasta de instalação ainda não existia. O usuário corrigiu o dono do volume e preparou as dependências:

bash -lc 'sudo chown "$(id -u):$(id -g)" "$HOME/.hermes/installs" && hermes pm repair && hermes --version'

Em seguida, o log mostrou que a integração WhatsApp estava habilitada e encerrava o gateway ao falhar na instalação npm do conector. Para usar apenas o CLI, o usuário desativou essa integração na configuração compartilhada com o host e confirmou que a interface abriu:

hermes config set platforms.whatsapp.enabled false
hermes

Essas correções foram aplicadas ao container e à configuração do usuário. Os testes anteriores de hermes --version não cobriam a abertura da interface com as integrações configuradas no host.

Correção permanente do volume de dependências

O erro de permissão foi reproduzido com hermes pm repair em um diretório descartável cujo installs pertencia ao root:

✗ install state is not writable by this user (.../installs/bceb66d11c12ceaa)
repro_exit=1

A imagem agora executa devbox-entrypoint antes do comando do Compose. Quando o usuário é vscode e /home/vscode/.hermes/installs é um ponto de montagem separado, ajusta os donos divergentes para o UID/GID atual. O comando usado é:

sudo -n find "$runtime" -xdev \
    \( ! -uid "$uid" -o ! -gid "$gid" \) \
    -exec chown -h "$uid:$gid" {} +

O script não segue links simbólicos. A preparação das dependências continua no comando do Compose, com tempo limitado. A configuração das integrações do Hermes permanece no host.
